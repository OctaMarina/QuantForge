Known Gaps & Corrections
This page lists hours that are missing or incomplete in the published archive. It also lists changes in behaviour that change how you read rows, and the corrections that we make to files that we already published. This information comes from an audit of all exchanges and data types against reference data from the exchanges. We completed the audit in September 2026.
Status of corrections
A corrected file replaces the original file under the same object key ({exchange}/{YYYY-MM-DD}/{HH}/{symbol}_{data_type}.parquet) and keeps the same schema. Thus, your download code does not need changes. Corrections marked Published include the full history of the affected files. If you downloaded affected hours before the publish date, download them again. Planned corrections are not in the files at this time. Under review means that we check how many published files have the problem, or if a source is available to recover the data, before we decide. We will not do a cleanup of the full archive for entries marked Not planned.
Changes in the 2026-10 data-quality release
This release corrects timestamp units, exchange clocks, volume units and order book resets. We found these problems in an audit of all collectors and processors in October 2026. For corrections to files that we already published, refer to Corrections to published history. For data that it is not possible to recover, refer to Partially affected periods.
Deployment status
Not yet deployed. When we deploy it, this section will show the first corrected hour for each exchange. Files for earlier hours keep the previous behaviour until we publish the corrections below.
Changes in behaviour in the 2026-10 data-quality release
 | Exchange ID | Data type | Before the release | From the release
 | bitget_futures, bitget_spot | ticker | price_change_percent as Bitget's fraction (0.0123 = 1.23 %) | price_change_percent in percent, the same as all other exchanges
 | kraken_spot | orderbook, ticker | event_time is our receive time in nanoseconds | event_time is our receive time in milliseconds
 | kraken_spot | trades | If we could not read the trade timestamp from Kraken, trade_time used our receive time in nanoseconds as a fallback | The fallback is our receive time in milliseconds
 | hyperliquid_spot, hyperliquid_futures | mark_price, open_interest | event_time and timestamp are our receive time in nanoseconds | Our receive time in milliseconds (the venue does not send a timestamp)
 | lighter | mark_price, ticker, open_interest | event_time and timestamp are our receive time in nanoseconds | Lighter's publication time in milliseconds (our receive time in milliseconds if a message does not have a publication time)
 | lighter | orderbook | event_time is our receive time; transaction_time is empty | event_time is Lighter's publication time and transaction_time is Lighter's matching-engine update time. Both are in milliseconds
 | bitget_futures, bitget_spot | orderbook | transaction_time is empty | transaction_time is Bitget's matching-engine time; event_time is the push time, as before
 | kraken_derivatives | open_interest (REST) | timestamp is the time of the last trade of the contract, in nanoseconds. On quiet markets, this time can be hours old | timestamp is the time at which Kraken sent the open interest, in milliseconds
 | kraken_derivatives | ticker (PI_, FI_) | base_asset_volume contains the contract count. For inverse contracts, this count is a USD amount | base_asset_volume is empty, because the exact base-coin volume needs the price of each fill. Linear PF_ contracts do not change
 | kraken_derivatives | candles (PI_, FI_) | base_volume contains the contract count (USD) | The same value is in quote_volume (USD); base_volume is empty
 | okx_futures | ticker (swaps) | quote_asset_volume = base volume × last price. This calculation uses the current price for all earlier fills | quote_asset_volume is empty, because OKX does not publish a quote turnover for swaps. base_asset_volume does not change
 | lighter | trades | Liquidation executions were missing (Lighter sends them separately from other trades). We dropped the trades that Lighter replays after a reconnect | Liquidation executions are included (order_type = liquidation), and replayed trades fill reconnect gaps. We still drop replayed trades from before the arrival hour
 | kraken_derivatives | trades, liquidations | We dropped the fills that Kraken replays after a reconnect | Replayed fills fill reconnect gaps, and we remove duplicate fills by trade ID. We still drop replayed fills from before the arrival hour
 | bybit, bybit_spot | orderbook | When we captured REST depth snapshots, we published them as order book resets. But their update IDs are from Bybit's 1,000-level stream, not from the 50-level stream that the order book uses | Only Bybit's WebSocket snapshots reset the order book
 | kraken_spot, lighter | orderbook | When we captured REST snapshots, we published them as order book resets. The Kraken REST snapshot has a maximum of 500 of the 1,000 levels and no sequence. The Lighter REST snapshot has no sequence number | Only the WebSocket snapshots of the venue reset the order book
 | binance_spot, binance_futures, aster_futures, okx_spot, okx_futures, hyperliquid_spot, hyperliquid_futures, kraken_derivatives | orderbook | We published no rows for a snapshot of an empty order book. Thus, a replayed order book kept its previous levels | An empty snapshot publishes one snapshot row with side = noop and the sequence of the snapshot. When you see this row, clear the order book
 | hyperliquid_spot, hyperliquid_futures | orderbook | We removed levels with an empty, zero or negative size from a snapshot, and gave no warning | If a snapshot has an invalid level, we do not publish any part of that snapshot. The replay report for the hour marks the order book as unverified until the next valid snapshot
 | okx_spot | orderbook (REST snapshot rows) | order_count was always 0, because we read it from a deprecated OKX field | order_count is the number of orders that OKX reports
 | bitget_futures | liquidations | If a liquidation did not have a valid price, we published its USD amount as the base quantity | We do not publish these liquidations
 | bybit | open_interest | The row at the start of the hour could miss updates that Bybit sent immediately before the hour but that we received immediately after it | The row at the start of the hour includes these updates. Its received_time is not earlier than the time when we received them
 | lighter | candles (spot) | Spot markets have the names that Lighter uses, for example ETH/USDC | Spot markets have the same names as in the trade and order book datasets, for example ETH_USDC
Changes from the 2026-09 data-integrity release
The changes that follow apply to files that we published from the 2026-09 data-integrity release onward. The table gives specific dates where necessary. Earlier files can keep the previous behaviour. A table below shows which corrections to historical files we plan. The venue notes on each data type page (for example trades and liquidations) tell you how to use older files.
Changes in behaviour from the 2026-09 data-integrity release
 | Exchange ID | Data type | Before the release | From the release
 | okx_spot, okx_futures | trades | One row for each taker order at each price level. The trades channel of the exchange combines fills, trade_id is the last fill ID and quantity is the sum of the sizes | One row for each fill (trades-all channel)
 | okx_futures | mark_price (funding rows) | event_time is the next settlement time (fundingTime), which is later than the time at which the rate was observed | event_time is the publish time of the funding message (ts); fundingTime is still in next_funding_time
 | okx_futures | ticker | base_asset_volume in contracts, quote_asset_volume in base coin | base_asset_volume in base coin (volCcy24h) for linear and inverse swaps; quote_asset_volume = base volume × last price (empty from the 2026-10 release, refer to the table above)
 | kraken_derivatives | mark_price | funding_rate is Kraken's absolute funding rate | funding_rate is Kraken's relative funding rate, a fraction for each funding period
 | kraken_derivatives | ticker | price_change contains Kraken's 24h change percentage; price_change_percent is not a percentage | price_change = last price − 24h open; price_change_percent = Kraken's 24h change percentage
 | kraken_spot | orderbook | Levels that went out of Kraken's 1,000-level window had no delete row. Thus, a replay had to truncate the order book | We publish levels that go out of the window as delete rows. Thus, a replay without more steps keeps 1,000 levels per side
 | kraken_derivatives | open_interest (PI_, FI_) | sum_open_interest_value = contracts × price | sum_open_interest_value = contracts × contract size (USD)
 | lighter | open_interest | sum_open_interest contains the USD notional | sum_open_interest in base units, sum_open_interest_value = USD notional
 | lighter | mark_price | funding_rate in percent; next_funding_time contains the last funding time | funding_rate as a fraction; next_funding_time is the next funding time
 | bybit | ticker | price_change_percent as a fraction (-0.0207 = -2.07 %) | price_change_percent in percent
 | bybit | ticker, mark_price, open_interest | Deltas with changes only: unchanged fields are null. An open interest file is available only for hours in which open interest changed | The full state for each symbol, carried forward. Each symbol with known open interest has a row at the start of the hour (timestamp and received_time = start of the hour)
 | bitget_futures | open_interest | sum_open_interest_value is empty | sum_open_interest_value = open interest (base coin) × mark price
 | binance_futures | ticker, mark_price, liquidations | COIN-M contracts (for example BTCUSD_PERP, BTCUSD_260925, with volumes and quantities in contracts) and delisted USDⓈ-M symbols were included | We publish only listed USDⓈ-M symbols under binance_futures
 | binance_spot, binance_futures, aster_futures | orderbook | We published each REST depth snapshot two times (on Binance, one copy has received_time = event time × 1e6) | Collectors that we started or restarted with the updated version on or after 2026-09-30 publish each REST depth snapshot one time
 | hyperliquid_spot, hyperliquid_futures | trades | Trades that the exchange replayed after a reconnect could occur again in the file of a later hour | We do not publish replayed trades again

Short reconnect gaps
Collectors reconnect at intervals (some venues require this) and after network errors. We cannot recover the data that the exchange sends during a reconnect. This causes gaps of some seconds, as follows:
Binance (spot and futures): We replace each connection about every 24 hours, because Binance requires this. Trades that Binance sends during the reconnect are missing and show as gaps in the trade IDs.
Bybit trades: Gaps from a few seconds up to about 3 minutes. Most of these gaps occur near a daily reconnect between about 02:00 and 02:50 UTC. We plan a backfill from Bybit's public trade archives.
Kraken spot: Reconnect gaps of 3–7 seconds. Sometimes, order book updates stop for 10–20 minutes while trades continue.
Hyperliquid: We can lose a small number of trades near reconnects.
If a venue gives sequence fields (order book update IDs, consecutive Binance trade IDs), use them to detect these gaps. For order books, discard the local order book at a gap. Then start again from the next snapshot.
BitMEX (historical dataset)
BitMEX is closed. BitMEX settled its perpetual contracts on 2026-09-16 at 12:00 UTC and delisted its spot pairs on 2026-09-21. On 2026-09-22, BitMEX announced "BitMEX Exchange Now Closed". We stopped the collection. You can download the bitmex dataset, from 2025-09-29 to 2026-09-22, through the Python SDK, the REST API and flat-file access. Files for the last hours contain little or no activity.
