Exchange Wire Formats
Binance Futures wire format
This page shows how Binance USDⓈ-M Futures messages become rows in our Parquet files. For each data type below, you see a real message next to the rows that we publish for it. The page also gives the source and the rule for each column. Put the pointer on a line or a column to see how they connect.
Checked against our pipeline
We recorded these messages from Binance USDⓈ-M Futures on 2026-10-05. Our test suite replays each message through the production collector parser and the postprocessor. The test fails if the published rows are different from the rows on this page. Files that we wrote before a change to the pipeline can be different. Refer to Known Gaps & Corrections.
Public WebSocket (order book, trades): wss://fstream.binance.com/public/stream?streams=<symbol>@depth@0ms/<symbol>@trade
Market WebSocket (ticker, mark price, liquidations): wss://fstream.binance.com/market/stream?streams=!ticker@arr/!markPrice@arr@1s/!forceOrder@arr
REST: https://fapi.binance.com
Exchange API reference: developers.binance.com. For the conventions that apply to all exchanges, refer to the wire formats overview.

One row per price level. Updates come from the <symbol>@depth@0ms stream. REST snapshots set the initial state of the order book.
WebSocket <symbol>@depth@0ms
REST GET /fapi/v1/depth

REST depth snapshot
The collector requests a REST snapshot when it connects. It also requests one after a sequence gap, when it must reset its order book. We publish only the snapshots that the collector applied to its order book. Each level becomes one snapshot row.
Shortened: We requested this example with limit=5 to keep it short. The collector requests limit=500, or limit=100 when it resets many order books at the same time.

received_time1791226529504069515—Our collector's clock when it received the REST response, in nanoseconds since the Unix epoch.
event_time1791226529372ECopied. Milliseconds.
transaction_time1791226529369TCopied. Milliseconds.
symbolBTCUSDT—The symbol that the collector requested.
event_typesnapshot—snapshot for every REST snapshot.
first_update_idnull—Null for snapshots.

prev_final_update_idnull—Null for snapshots.
last_update_id11742279126574lastUpdateIdCopied. Replay from the first later update that has first_update_id ≤ this value ≤ final_update_id, or that has prev_final_update_id equal to this value.
sideaskbidsasksbid for levels in bids, ask for levels in asks. One row per level.
price85583.20bids[][0]asks[][0]Copied as the exact decimal string.
quantity5.022bids[][1]asks[][1]Copied as the exact decimal string.
order_countnull—Null. Binance does not send order counts.
Notes
We do not publish an update row if its final_update_id equals the lastUpdateId of a snapshot in the same hour. The snapshot already contains these updates.
A depth update with no levels becomes one row with side noop, and with price and quantity 0. This row contains the update IDs and does not change the order book. An empty REST snapshot becomes one noop snapshot row. When you replay this row, clear the order book.
REST snapshots usually contain 500 levels per side. When the collector resets many order books at the same time, the snapshots contain 100 levels per side. Levels outside a snapshot are unknown until an update changes them.
Binance can send a removal (quantity 0) for a level that is not in the order book. The Binance documentation says that this is normal. Ignore the removal when you replay.
A file can start with a checkpoint. A checkpoint is the order book that we replayed up to the hour boundary, as snapshot rows. These rows have received_time at the start of the hour and the event_time of the last exchange event before that time. Their transaction_time is null. Their final_update_id and last_update_id contain the last update ID that we applied. We write a checkpoint only after we make sure that the order book is current. If a file has no checkpoint, continue from the order book of the previous hour or wait for the next snapshot.
For the column types and descriptions, refer to the Order Book schema.

Open Interest
One row per 5-minute open interest point from REST polls.
REST GET /futures/data/openInterestHist
The USDⓈ-M WebSocket streams of Binance do not include open interest. The collector polls the history of 5-minute open interest every 5 minutes. We publish each point one time, in the hour of the first poll that returned it.
Shortened: We requested this example with limit=3 to keep it short. The collector requests limit=500.
